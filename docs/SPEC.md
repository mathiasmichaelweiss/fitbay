# FitBay: спецификация переезда из прототипа в React-приложение

Версия 1.0 · 11.10.2026 · автор: Mathias + Claude
Источник правды по функциям: прототип `kalorii.html` (версия 138, артефакт FitBay). Если что-то в этом документе расходится с прототипом, прототип показывает задуманное поведение, а этот документ задаёт архитектуру и порядок работ.

Документ написан для ИИ-агента, который будет вести разработку. Каждая задача в конце (to-do list) самодостаточна: цель, что сделать, критерий готовности.

---

## 1. Цель и границы

**Цель.** Перенести функционально готовый прототип в нормальное приложение:
- **Блок A (локально и бета).** Веб-приложение на React, бесплатный хостинг, база DynamoDB в существующем AWS-аккаунте BewerGO (новые таблицы), вход через Auth0. Тестируют брат (тренер-партнёр) и 3-10 человек из Instagram.
- **Блок B (rollout и production).** Отдельный AWS-аккаунт FitBay, свой домен, своя инфраструктура, оплаты (Stripe и сторы), нативные приложения iOS/Android через Capacitor, Apple Health / Health Connect, бэк-офис.

**Не цель.** Не переносить прототип построчно. Прототип это один HTML-файл на 3 000+ строк с наслоениями. Переносим поведение, а код пишем заново, модульно.

**Продуктовый принцип при переносе.** В бете показываем только то, что нужно в первую неделю. Остальное прячем за понятными разделами и подсказками (см. раздел 6, UX).

## 3. Роли

- **Клиент.** Ведёт питание, тренировки, вес, самочувствие. Может работать без тренера (с ИИ-коучем).
- **Тренер.** Всё, что у клиента, плюс кабинет: клиенты, расписание, планы, пакеты, обзор денег. Платит ту же подписку, если не партнёр.
- **Партнёр-тренер.** Тренер без подписки, с кодом для клиентов (клиенты по коду без комиссии). Пример: брат.
- **Студия.** Группа тренеров со ступенчатой комиссией (см. финмодель). В блоке A только как атрибут тренера.
- **Владелец (admin).** Mathias. Бэк-офис, роли, тестовые пользователи.

## 4. Функциональные модули (что переносим)

Ниже перечень того, что уже работает в прототипе. Для каждого модуля агент открывает соответствующие функции в `kalorii.html` и переносит поведение.

### 4.1 Расчётное ядро `@fitbay/calc` (обязательно первым)
Правило архитектуры: **один источник правды**. Все производные числа (норма, расход, бонус активности, дефицит, жир, прогноз) считаются только здесь. Экраны только отображают.
Перенести из `CALC` в прототипе:
- `bmr` (Миффлин), `factor` (активность), `actKcal`, `bonus` (доля сожжённого 0/50/100%), `expenditure`
- `target(profile, day)` с приоритетом источников: гибкий план фазы → БЖУ фазы → калории фазы (% или ккал) → ручные БЖУ клиента → гибкий план клиента → авто по цели
- `phase`, `phaseTarget`, `flexOf`, `dayType` (тренировка в журнале, запись к тренеру, дни недели, ручной override)
- `leanShare`, `fatFromDeficit`, прогноз веса, анализ веса (`WEIGHT.analyze`)
- прогрессия по неделям `progT`, неделя фазы `phWeek`
- план и факт `pvf` (score, статусы ok/over/under/miss)
- счётчик пакета `pkgUsage`, разбор занятий по умолчанию `pkgSessDefault`
- чек-ин: `ciAvg`, `ciBad`
Покрыть юнит-тестами: каждая функция минимум 3 кейса, включая граничные.

### 4.2 Питание
- Дневник по дням, слоты (завтрак, обед, ужин, перекус), кольца калорий и БЖУ, прогноз на день.
- Режимы ввода: фото, текст (в т.ч. рассказ за день), «Мои блюда» (рецепты), ручной ввод.
- Редактор результата: ингредиенты, масштаб порции, граммы, посуда и заполненность.
- Оценка веса по фото: правила масштаба (ладонь, вилка, пиалка), плотности по типу блюда, поправка на перспективу.
- Личные поправки веса и **общая база поправок** (последние 30 по блюду, медиана, отсев выбросов, коэффициент в промпт). Пользователь не знает, что поправка уходит в общую базу.
- Гибкий план: стандартный или по типу дня (тренировка / отдых), чип типа дня на главной.
- Ручные БЖУ клиента (если у клиента нет плана тренера).
- ИИ-коуч на день с учётом уже съеденных приёмов (слоты в промпте).

### 4.3 ИИ (бэкенд-прокси)
- Все вызовы идут через `POST /ai/{task}`. Ключ OpenAI только на сервере.
- Задачи: `food_photo`, `food_text`, `day_story`, `coach`, `activity`, `recipe`, `workout_ai`, `plan_ai`, `label_ocr` (блок B).
- Модель по умолчанию GPT-5.6 Luna. Модель настраивается **для каждой задачи отдельно** (конфиг в базе), чтобы менять без релиза.
- Дневные лимиты (полная подписка): еда 30, активности 10, ИИ-тренер 5, рецепты 20. В пробный период ниже. При лимите мягкое сообщение без слова «лимит». Unlimited-тариф: мягкий потолок 100 в день.
- Коуч не перезапрашивается, если после прошлого совета не было новой еды.
- Промпты переносятся из прототипа как есть (они отлажены), хранятся в `services/api/prompts/*.ts`.
- Логировать токены по каждому вызову (для расчёта реальной стоимости пользователя).

### 4.4 Тренировки
- Библиотека упражнений (Free Exercise DB, картинки on demand со стилем из бэклога RM-16).
- Журнал: подходы, повторы, вес, отметка выполнения, история, редактирование.
- Комментарии и метки (боль, легко, тяжело, техника) к тренировке и к упражнению.
- Мои программы, ИИ-тренер (дом / зал, инвентарь).
- Глобальный виджет активной тренировки поверх всех экранов (и у клиента, и у тренера).
- Прогрессия по неделям (+кг или +повторы в неделю), бейдж «Неделя N», подстановка веса недели при старте.
- План и факт: при старте тренировки из плана сохраняется назначенное, после неё таблица план/факт с процентом.

### 4.5 Тренер и маркетплейс
- Каталог тренеров с поиском и фильтрами, профиль тренера, коды только для партнёров.
- Пакеты тренера, заявки на пакеты, генератор пакета (частота, формат, срок, питание, скидки).
- Расписание (неделя / месяц), слоты, бронирование, защита от двойной брони на уровне базы (conditional write).
- Карточка клиента: питание, анализ поведения, вес и замеры, активность, самочувствие, тренировки (карточки + дровер), рекомендации, «до/после», план целей.
- План целей: фазы (сушка, набор, удержание, рекомпозиция, своя), калории по %/ккал/БЖУ/гибко, условия перехода, тренировки и питание фазы, ИИ-генерация плана, автопереход фаз, маршрут-таймлайн у клиента.
- **Архив планов клиента**: при изменении плана тренером старый план уходит в архив клиента (до 10), клиент может забрать тренировки себе.
- Шаблоны планов тренера (личные).
- Совместная тренировка: тренер запускает тренировку за клиента, статус «в процессе», заметки тренера только к совместным занятиям.
- Счётчик занятий в пакете: автосписание после прошедшего занятия, ручное списание и возврат **с записью в журнал и уведомлением клиента** (защита от жульничества).
- Отмена: клиент бесплатно за 24 часа и раньше, позже занятие сгорает. Тренер отменяет, и занятие остаётся у клиента. Причина отмены приходит второй стороне.
- Обзор денег: выручка за месяц и по месяцам, «чистыми» после комиссии, активные клиенты, занятия, оплачено вперёд, заканчивающиеся пакеты, топ клиентов.

### 4.6 Оплаты (блок B, архитектуру закладывать в A)
- **Услуги тренера** (пакеты, персональные, онлайн): Stripe Connect (Express), комиссия FitBay как `application_fee` по ступеням (12,5% соло, 10% / 8% / 6% студии, партнёры от 5% или 0 по коду). Выплаты тренерам в версии 2, но модель данных готовим сейчас.
- **Подписка FitBay** (9,99 €/мес, 69,99 €/год, Unlimited 14,99 €/мес):
  - зарегистрировался в вебе → Stripe Billing;
  - в нативке → App Store / Google Play (рекомендуется RevenueCat как единый слой статусов);
  - единый статус `entitlement` у пользователя, независимо от источника.
- Вебхуки Stripe и сторов → Lambda → обновление `entitlement` в DynamoDB.

### 4.7 Самочувствие, вес, замеры
- Ежедневный чек-ин (сон, энергия, стресс, голод, боль, соблюдение плана), плитка, тепловая карта с лупой по касанию, сигнал тренеру при 3 плохих днях.
- История веса с диапазонами (неделя, месяц, 3 мес, год, всё), скользящее среднее, прогноз, цель.
- Замеры тела, напоминание о замерах.

### 4.8 Уведомления
- В блоке A: колокольчик внутри приложения (все типы из прототипа: рекомендации, план тренера по разделам, записи, отмены, боль на тренировке, самочувствие, пакеты, ручные списания).
- В блоке B: пуш (Firebase Cloud Messaging / APNs через Capacitor), e-mail для важного (отмена, списание).

### 4.9 Прочее
- Онбординг, согласия DSGVO (версионируются), «Мои данные» (экспорт JSON, удаление аккаунта).
- «До и после» с проверкой тренером.
- Студии рядом (карта Leaflet, пробное занятие), пока на демо-данных.
- Тестовые пользователи для владельца (переключение без влияния на личный аккаунт).

## 5. Данные (DynamoDB)

### 5.1 Таблицы
Блок A, аккаунт BewerGO, регион `eu-central-1`:
- `fitbay-main` (single-table, все сущности)
- `fitbay-shared-food` (общая база поправок веса и, в блоке B, продукты по штрих-кодам)

PITR включён, TTL поле `ttl` для временных записей (лимиты ИИ по дням).

### 5.2 Ключи и сущности `fitbay-main`
PK / SK строками, GSI для обратных запросов.

| Сущность | PK | SK | Основные поля | Источник в прототипе |
|---|---|---|---|---|
| Пользователь, профиль | `USER#<uid>` | `PROFILE` | sex, birth, h, w, tw, act, goal, macro, flex, dayOv, lang, consents, role, entitlement | `settings` |
| Приём пищи | `USER#<uid>` | `MEAL#<date>#<ts>` | name, kcal, p, f, c, grams, items[], plate, slot, photoKey | `meal` |
| Рецепт | `USER#<uid>` | `RECIPE#<id>` | p100, grams, items | `recipe` |
| Совет коуча | `USER#<uid>` | `COACH#<date>` | text, key | `coach` |
| Замер | `USER#<uid>` | `MEASURE#<date>` | weight, waist, ... | `measure` |
| Тренировка | `USER#<uid>` | `WORKOUT#<date>#<ts>` | title, items[], tags, note, plan (план и факт), kcal | `workout` |
| Активная тренировка | `USER#<uid>` | `WOACTIVE` | forClient, items | `woactive` |
| Программа | `USER#<uid>` | `PROGRAM#<id>` | items, src | `program` |
| Активность | `USER#<uid>` | `ACT#<date>#<ts>` | min, km, steps, kcal | `activity` |
| Чек-ин | `USER#<uid>` | `CHECKIN#<date>` | sleep, energy, stress, hunger, pain, adh, note | `ci-*` |
| Поправки веса (личные) | `USER#<uid>` | `WCORR` | list (последние 30) | `wcorr` |
| Шаблон тренера | `USER#<uid>` | `TPL#<id>` | phases | `tpl` |
| Использование ИИ | `USER#<uid>` | `USAGE#<date>` | счётчики, tokens, ttl | `usage` |
| Тренер | `TRAINER#<tid>` | `PROFILE` | uid, name, partner, code, packages[], rates, studioId, hidden | `trainers` |
| Связь клиент-тренер | `TRAINER#<tid>` | `CLIENT#<uid>` | consent, since, ref | `coach/<uid>` (вместо снапшота) |
| План клиента | `USER#<uid>` | `PLAN` | phases, current, phaseStart, startW, history, changes, archive[] | `plans` |
| Рекомендации | `USER#<uid>` | `TIPS` | items[] | `tips` |
| Слот | `TRAINER#<tid>` | `SLOT#<start>#<id>` | dur, place, addr, bookedBy, plan, session, tnote, live, cancel, burned, cancelledFor | `slots` |
| Заявка/пакет | `TRAINER#<tid>` | `REQ#<id>` | uid, pkg, status, sessions.total, adj, log[] | `req` |
| До/после | `USER#<uid>` | `BA` | photos, status | `ba` |
| Студия | `STUDIO#<sid>` | `PROFILE` | name, address, trainers, commission tier | новое |

GSI:
- `GSI1` (PK `GSI1PK` = `CLIENT#<uid>`, SK `GSI1SK`): слоты и заявки клиента (`bookedBy`, `req.uid`, `cancelledFor`)
- `GSI2`: каталог тренеров (`CATALOG`, сортировка по order)
- `GSI3`: код партнёра → тренер

**Важное изменение против прототипа.** В прототипе клиент периодически пишет снапшот своих данных в `coach/<uid>` для тренера. В новом приложении снапшота нет: тренер читает данные клиента через API, а API проверяет связь `TRAINER#/CLIENT#` и согласие (`consent`). Так данные не дублируются, а доступ контролируется сервером.

### 5.3 Права доступа (проверяет Lambda)
- Свои данные: только владелец.
- Данные клиента: тренер, у которого есть связь и действующее согласие клиента.
- Слоты: тренер пишет свои; клиент может забронировать свободный слот (conditional write `attribute_not_exists(bookedBy)`) и отменить свой.
- Заявки и журнал списаний: только тренер меняет счётчик, каждое изменение пишет запись в `log` (неизменяемо).
- Общая база поправок: пишет любой пользователь (свои записи), читает сервер для подсказки ИИ.
- Админ: всё, через бэк-офис.

### 5.4 Миграция данных из прототипа
Скрипт `infra/scripts/migrate-from-artifact.ts`: читает JSON-экспорт (кнопка «Мои данные → экспорт» в прототипе) и пишет в `fitbay-main`. Для личного аккаунта Mathias обязательно: его реальные данные питания и веса должны переехать без потерь.

## 6. UX-перепаковка (до или вместе с переносом)

Проблема прототипа: функций много, нет единого простого пути. Цель: новый пользователь за 1 минуту понимает, что делать.

**Навигация клиента (нижняя панель, 4 раздела):**
1. **Сегодня**: калории и белок, добавить еду, самочувствие, совет коуча, следующая тренировка.
2. **Тренировки**: начать, мои программы, история, план тренера (если есть).
3. **Прогресс**: вес, замеры, фото «до/после», маршрут плана.
4. **Тренер**: мой тренер, запись, пакеты, каталог (если тренера нет).
Настройки и колокольчик в шапке.

**Навигация тренера:** переключатель «Я / Кабинет». Кабинет: Клиенты, Расписание, Обзор, Шаблоны.

**Подсказки:**
- онбординг по роли (клиент, тренер, студия), 3-4 экрана;
- при первом открытии каждого раздела одна подсказка (coach mark), которую можно закрыть;
- «?» с дровером справки уже есть в прототипе, сохранить и дописать для новых разделов.

**Прогрессивное раскрытие:** гибкий план питания, ручные БЖУ, прогрессия по неделям и шаблоны спрятаны в «Дополнительно» и не показываются в первую неделю.

**Мобильные требования:** поля ввода 16 px (без зума на iOS), без горизонтального скролла, safe-area, тач-цели не меньше 44 px.

## 7. Нефункциональные требования

- **DSGVO.** Данные питания и тела это данные о здоровье (ст. 9). Нужны: явное согласие, согласие на доступ тренера, экспорт и удаление, AV-договоры с AWS, Auth0, OpenAI, Stripe, хранение в ЕС (`eu-central-1`), политика конфиденциальности с упоминанием обезличенных поправок веса и данных Open Food Facts.
- **Без обещаний результата** в текстах продукта.
- **Безопасность.** Ключи только на сервере, presigned URL для фото, rate limiting на API, логи без персональных данных.
- **Производительность.** Первый экран меньше 2 с на 4G, офлайн-очередь для записи еды (блок B).
- **Наблюдаемость.** CloudWatch логи и алерты, Sentry на фронте.

## 8. Тестирование

- Юнит: `@fitbay/calc` (покрытие 90%+).
